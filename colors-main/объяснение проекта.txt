Проект состоит из двух половин, которые общаются по HTTP:
Сервер — app.py (Python + Flask). Он принимает запросы браузера, крутит логику, лазит в базу и файлы, и отвечает страницами.
Страницы — папка templates/ (HTML с вставками Jinja). Сервер подставляет в них данные и отдаёт браузеру уже готовый HTML.
Данные живут в двух местах: database.sqlite3 (таблицы users и palettes) и папка uploads/ (сами фотографии). Схема простая:
браузер  --запрос (GET/POST)-->  Flask (app.py)  -->  база / файлы / Pillow
браузер  <--страница или редирект--  Flask        <--  результат
Flask работает как таблица «адрес → функция»: каждая @app.route('/login') означает «когда придут на этот адрес, вызови эту функцию». Функция возвращает либо страницу (render_template), либо редирект (redirect).
app.py по кускам
1. Константы и настройки (верх файла). UPLOAD_FOLDER и DB_PATH — где лежат фото и база (рядом с app.py). ALLOWED_EXTENSIONS — белый список расширений. MIN_COLORS/MAX_COLORS — границы 1–16. app.secret_key — ключ для подписи сессий. MAX_CONTENT_LENGTH — лимит 10 МБ: файл больше Flask отклонит сам ошибкой 413.
2. База данных. get_db() открывает соединение; строчка conn.row_factory = sqlite3.Row нужна, чтобы к строкам результата обращаться по именам колонок (row['username']), а не по номерам. init_db() создаёт таблицы через CREATE TABLE IF NOT EXISTS — при повторном запуске ничего не перетирается. В users: id, имя (UNIQUE — база сама не даст дубликату), хэш пароля. В palettes: id, user_id (владелец), название, имя файла фото, colors_json (палитра, упакованная в JSON-строку — у SQLite нет типа «список», поэтому храним строкой и разбираем обратно через json.loads), дата.
3. Пароли. Сам пароль не хранится. make_hash генерирует соль (случайную строку) и считает sha256(соль + пароль), сохраняет «соль$хэш». check_hash при входе берёт сохранённую соль, считает хэш введённого пароля и сравнивает. Смысл: из украденной базы пароли не прочитать, а у одинаковых паролей хэши разные из-за разной соли.
4. Названия цветов. COLOR_NAMES — список эталонов «(RGB, название)». color_name(rgb) ищет ближайший эталон: min по ключу — сумме квадратов разниц по трём каналам. Поэтому HEX точный, а название приближённое — это честное свойство алгоритма «ближайший цвет».
5. extract_palette — сердце проекта, по шагам:
Если у картинки есть прозрачность (RGBA/P с transparency) — клеим её на белый фон, иначе прозрачные места станут чёрными и испортят палитру.
convert('RGB') — приводим любой формат (png, jpg, gif) к одному виду.
thumbnail((120, 120)) — уменьшаем картинку на месте: для палитры хватит 14 тысяч пикселей вместо миллионов, так быстрее.
quantize(colors=n) — готовый алгоритм Pillow (median cut): он группирует все оттенки изображения в n кластеров-цветов. Писать свой k-means не нужно.
convert('RGB') + getcolors(...) — считаем, сколько пикселей досталось каждому цвету.
Сортировка по убыванию счётчика — самые «весомые» цвета первыми.
Сборка результата: '#%02x%02x%02x' % rgb превращает три числа 0–255 в HEX-строку (по две шестнадцатеричные цифры на канал), color_name даёт название, percent — доля пикселей.
6. allowed_file — проверка расширения по белому списку: берём часть имени после последней точки и смотрим, есть ли она в ALLOWED_EXTENSIONS.
7. login_required — декоратор. Это функция-обёртка: она принимает функцию-страницу и возвращает новую, которая сначала проверяет session['user_id']; нет — flash «Сначала войдите» и редирект на вход; есть — вызывает оригинальную страницу. Запись @login_required над маршрутом = «перед этой страницей выполни проверку». @wraps(view) сохраняет имя исходной функции, чтобы Flask не путался.
8. session и flash. session — блокнот Flask, который живёт в подписанной куке браузера: там user_id, username и pending (результат последнего анализа). Подпись значит: пользователь не может подделать себе чужой user_id. flash — одноразовое сообщение: кладётся в session, страница забирает его через get_flashed_messages, показывает — и оно удаляется. Поэтому сообщения не повторяются после обновления страницы.
9. Маршруты, что где происходит:
/register: GET — показать форму; POST — проверить длины, SELECT-ом убедиться, что имя свободно, INSERT в users, редирект на вход.
/login: POST — найти пользователя по имени, check_hash; совпало — записать session и на главную; нет — flash об ошибке.
/logout: удалить несохранённый загруженный файл, session.clear().
/: отдать index.html, передав в шаблон pending из session.
/analyze: цепочка проверок (число ли количество и в диапазоне → есть ли файл → расширение → размер → «открывается ли как картинка» через Image.open), сохранение файла под именем uuid4().hex (случайное имя: файлы не перетирают друг друга и чужой файл не угадаешь по адресу), анализ, запись в session['pending'], редирект.
/uploads/<name>: отдать файл фото; send_from_directory не даст выйти за пределы папки uploads хитрым именем.
/save: взять pending, INSERT в palettes (палитра — JSON-строкой), pending очистить, редирект в «Мои палитры».
/palettes: SELECT своих палитр по user_id, json.loads обратно в списки, передать в шаблон.
/delete/<id>: проверить, что палитра своя (иначе 404 — чужую даже «не найдём»), удалить строку; файл с диска удалить только если ни одна другая палитра на него не ссылается.
/export/<id>/<fmt>: txt — собрать текст и отдать файлом; png — нарисовать полоску цветов через Pillow и отдать картинкой.
errorhandler(413) и errorhandler(404) — перехват ошибок «файл слишком большой» и «адрес не найден», чтобы показать понятное сообщение/страницу вместо технической простыни.
10. Почему после POST почти всегда redirect. Это шаблон POST-Redirect-GET: обработали данные → отправили браузер за новой страницей. Тогда кнопка F5 не отправляет форму повторно, а flash показывается ровно один раз.
11. if __name__ == '__main__': — защита от случайного запуска при импорте: check_examples.py импортирует из app функцию, и сервер при этом не должен стартовать; а запуск python app.py попадает в эту ветку и стартует сервер.
HTML (templates)
Jinja — мост из Python в HTML. Браузер Jinja не видит никогда: сервер подставляет всё до отправки.
{{ ... }} — подставить значение: {{ c.hex }}, {{ session['username'] }}.
{% if pending %} … {% else %} … {% endif %} — ветвление: есть результат анализа или нет.
{% for c in pending.colors %} … {% endfor %} — цикл: блок .pal-item повторится по разу на каждый цвет.
{% extends 'base.html' %} + {% block content %} — наследование: base.html держит общий каркас (шапка, блок flash-сообщений, весь CSS в одном <style>), а каждая страница вставляет внутрь только своё содержимое. Поэтому стиль правится в одном месте.
Формы — как данные доезжают до Python.
method="post" — данные идут в теле запроса (GET вплёл бы их в адресную строку, а пароль в URL — плохо).
enctype="multipart/form-data" — без этого атрибута файл не загрузится вообще, форма умеет слать только текстовые поля.
name="photo", name="colors_count", name="username" — эти имена и есть ключи, которыми сервер читает данные: request.files.get('photo'), request.form.get('colors_count'). То есть связь HTML и Python держится на совпадении этих имён — переименуешь input, и сервер получит None.
action="{{ url_for('analyze') }} — куда отправлять; url_for строит адрес по имени функции-маршрута, чтобы не писать адреса руками и не ломать всё при их смене.
Немного JavaScript в index.html (две маленькие штуки). Первое: слушатель события change на input file — выводит имя выбранного файла текстом (браузер сам до отправки формы его почти не показывает). Второе: кнопки «копировать» — Jinja записывает HEX в атрибут кнопки data-hex="{{ c.hex }}", а JS по клику читает btn.dataset.hex и кладёт в буфер через navigator.clipboard.writeText, меняя надпись на «скопировано» на секунду. JS здесь только для удобства, вся логика — на сервере.
palettes.html — тот же принцип: {% if items %} и цикл по карточкам; у карточки фото (<img src="{{ url_for('uploads', name=item.image_file) }}">), чипы цветов с подсказкой title, кнопки экспорта и форма удаления с onsubmit="return confirm(...)" (подтверждение в браузере).
Путь одного действия целиком (анализ фото)
Клик «Получить палитру» → браузер шлёт POST /analyze с файлом и числом цветов.
analyze: проверки → файл сохранён как uploads/<uuid>.png → Image.open → extract_palette → список словарей положен в session['pending'] → ответ «редирект на /».
Браузер делает GET / → index() → render_template('index.html', pending=...).
Jinja: срабатывает ветка {% if pending %}, цикл рисует строки палитры, сервер подставляет HEX в style="background:..." → браузер получает чистый HTML.
Браузер отдельно тянет фото запросом GET /uploads/<uuid>.png.
«Сохранить палитру» → POST /save → строка в таблице palettes → редирект → GET /palettes → SELECT → карточки.
Короткие ответы на вероятные вопросы по коду
Декоратор? Функция-обёртка: добавляет проверку входа перед страницей, не трогая её код.
Зачем соль? Одинаковые пароли дают разные хэши, из базы пароли не восстановить.
Зачем uuid в имени файла? Нет коллизий имён и нельзя подобрать чужой файл по адресу.
Почему quantize? Готовая кластеризация цветов в Pillow; своя реализация k-means для учебного проекта избыточна.
Почему палитра в БД как JSON? У SQLite нет типа «список»; строка JSON парсится обратно одной функцией.
Почему redirect после POST? F5 не отправляет форму повторно, flash живёт один показ.
Где проверяется «это действительно картинка»? Image.open + img.load() в try/except: переименованный txt упадёт здесь, а не позже.
